# Task 拆分与问题描述规范

来源:协作反馈(2026-11-10)。目的:让 Task 可跟踪、问题描述可直接开发,减少反复确认。

## 1. 设计稿补充 → 新建 Task

**场景:** 前一天开发时还没有设计稿,后来新增了设计稿。

**做法:** 为新增设计单独建立 Task,不要并入原 Task。Task 中必须写明:
- 本次新增设计对应的**开发范围**(哪些页面/组件/交互);
- **验收标准**;
- 设计稿链接(Figma 等)。

## 2. 测试问题与优化项 → 分别建 Task

**场景:** 测试中发现的问题,以及后续提出的 UI/交互优化。

**做法:** 两类分别建立 Task,不要混在一起,否则难以跟踪。每个 Task 写明:
- **修改内容**;
- **验收标准**;
- **优先级**。

| 类型 | 说明 | 标签建议 |
| --- | --- | --- |
| 测试问题(Bug) | 与预期/需求不一致的缺陷 | Bug |
| 优化项 | UI/交互改进,非缺陷 | Improvement |

## 3. 问题描述要具体

避免"好像有问题""需要调整"这类描述。应补充:
- **具体现象**:在哪个页面/操作下,看到什么,期望是什么;
- **复现步骤**(Bug 适用);
- **相关链接**:需求文档、设计稿、截图或录屏。

这样开发可以准确理解,减少反复确认。

### 对比示例

| 不推荐 | 推荐 |
| --- | --- |
| 列表好像有问题 | WSO 详情表在筛选 Well 后,KPI 列显示为空;期望显示最近一次值。附:需求链接 / 截图 |
| 这个按钮需要调整 | 按钮高度改为设计稿 v2 的 32px,颜色用 primary;设计稿链接:…… |

## 4. Task 描述模板

```markdown
**类型:** Bug / Improvement / 设计稿新增
**优先级:** P0 / P1 / P2
**修改内容:** (具体现象 → 期望结果)
**开发范围:** (设计稿新增时必填)
**验收标准:**
- [ ] ……
**相关链接:** 需求文档 / 设计稿 / 截图
```
