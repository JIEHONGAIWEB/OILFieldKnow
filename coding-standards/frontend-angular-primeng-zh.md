# 前端编码规范 — Angular + PrimeNG(中文版)

> 英文原版:[frontend-angular-primeng.md](frontend-angular-primeng.md)(以英文版为准,两者需保持同步)。
>
> **本项目所有前端代码的权威规范。**
> 适用于前端应用(`wpo-app`,见 [../frontend/README.md](../frontend/README.md))中所有 `*.ts`、`*.html`、`*.scss` 的改动。
> 所有前端代码——无论是人工编写还是 AI 助手生成——都**必须**遵守这些规则。编写新代码和评审变更时均需使用。

角色设定:以资深 Angular 架构师的身份、具备深厚的 PrimeNG 专业能力,严格、精确且有建设性地执行规则。

## 1. 命名规范

- 1.1 组件、服务等的文件名**必须**使用 kebab-case(如 `user-profile.component.ts`)。
- 1.2 同一组件的 TS、HTML、SCSS 文件**必须**使用相同的基础名称。
- 1.3 类、接口、类型、枚举、组件、指令、管道、服务和模块**必须**使用 PascalCase。
- 1.4 变量、函数和方法参数**必须**使用 camelCase。
- 1.5 常量**必须**使用 UPPER_SNAKE_CASE。
- 1.6 所有命名**必须**语义清晰并与业务相关。

## 2. 代码风格与 TypeScript 规则

- 2.1 默认使用 `const`;仅在需要重新赋值时使用 `let`;禁止使用 `var`。
- 2.2 禁止使用 `any`,改用具体类型或 `unknown`。
- 2.3 生产代码中禁止出现 `console.log` / `debugger`。
- 2.4 所有函数**必须**显式声明返回类型。
- 2.5 所有公共方法**必须**有完整的 JSDoc 注释。
- 2.6 所有 HTTP 请求和 PrimeNG 事件异常**必须**被捕获并正确通知用户。
- 2.7 固定的状态/类型值使用枚举;禁止魔法字符串和魔法数字。
- 2.8 所有复杂对象**必须**使用显式的 `interface` 或 `type`;禁止使用无类型的内联对象。
- 2.9 禁止空的 `catch` 块;错误**必须**被处理或重新抛出。
- 2.10 移除所有未使用的导入、变量、参数和死代码。
- 2.11 移除大段被注释掉的代码,历史记录交给 Git。
- 2.12 使用严格相等 `===`,而不是 `==`。
- 2.13 对频繁的提交/点击事件增加防抖(debounce),防止重复请求。
- 2.14 使用可选链 `?.` 和空值合并 `??` 避免空指针风险。

## 3. 逻辑与缺陷预防

- 3.1 识别缺陷、性能风险、可维护性问题和安全漏洞。
- 3.2 遵循 Angular 官方最佳实践:变更检测、依赖注入(DI)、RxJS 的使用。
- 3.3 审查 PrimeNG 组件的使用:生命周期、事件绑定、模板语法、性能。
- 3.4 所有手动 `subscribe()` **必须**使用 `takeUntilDestroyed` 或 `takeUntil` 取消订阅。
- 3.5 禁止通过 `document.querySelector` 直接操作 DOM;使用 `Renderer2` 或宿主绑定(host bindings)。
- 3.6 将重复逻辑提取为可复用函数或私有方法。
- 3.7 避免空的 `if` 块、冗余条件或恒为真的表达式。
- 3.8 并行且相互独立的异步调用使用 `Promise.all`;避免顺序等待。
- 3.9 优先使用 `async/await`,避免深层回调嵌套。

## 4. 性能与架构

- 4.1 组件**必须**遵循单一职责原则;拆分过于庞大的"上帝组件"。
- 4.2 保持实现简单;避免对基础需求过度设计。

## 5. 国际化(i18n)

- 5.1 所有面向用户的文本**必须**使用翻译管道或服务;禁止硬编码字符串。
- 5.2 翻译 key **必须**遵循分层模式 `MODULE.FEATURE.KEY`;避免 `text1`、`label` 这类含糊的 key。

## 6. 样式(SCSS/CSS)

- 6.1 禁止内联静态样式;所有样式提取到样式表。
- 6.2 使用 `::ng-deep` 时,始终用 `:host` 限定作用域,防止全局样式污染。
- 6.3 尽量少用 `::ng-deep`;优先使用 PrimeNG 的 `styleClass`、`pt` 或 CSS 变量。
- 6.4 禁止使用 `!important`。
- 6.5 使用主题颜色变量,而不是硬编码的十六进制色值。

## 7. HTML 结构与语义

- 7.1 在合适的地方使用语义化 HTML 标签。
- 7.2 所有 `<img>` 标签**必须**包含有意义的 `alt` 属性。

## 8. 代码组织(复杂功能的分组与分布)

适用于**功能复杂**的文件/模块(条目多、职责杂、config/builder/导出项多)。简单文件无需强行分组。

- 8.1 复杂功能**必须**按职责**分组**,同一组的代码放在一起,不要按"想到什么写什么"的顺序堆叠。
- 8.2 每个分组**必须**有一行**中文分组注释**作为标题,例如
  `// ==================== 常量与枚举 ====================`。
- 8.3 默认分组顺序(可按实际裁剪,但相对顺序保持一致):
  类型/接口 → 枚举与常量 → 配置 → 工具/纯函数 → 核心逻辑(类/服务/Builder)→ 导出。
- 8.4 **导出顺序**与分组顺序一致,同类导出相邻;对外导出(`export` / barrel `index.ts`)集中管理,
  不在文件中间零散穿插。
- 8.5 注释使用**中文**,说明"做什么 / 为什么",不复述代码字面含义。
- 8.6 **新增或修改的部分必须同步补充中文注释**,并放入所属分组,不得追加在文件末尾了事。
- 8.7 过大的文件按分组拆分到多个文件(分布),各文件职责单一;拆分后用 `index.ts` 统一导出。
- 8.8 整理仅调整**顺序、分组与注释**,不得改动逻辑与行为;整理与功能变更分开提交。

## 评审输出格式

依据本规范进行代码评审时,按以下格式输出:

### 【问题摘要】

逐条列出违规项,格式为:

`规则 X.X · 第 X 行 · 问题描述(清晰简洁)`

### 【修复建议】

为每个问题提供可直接复制的代码示例,按文件类型(TS / HTML / SCSS)分组。

补充评审规则:

- 仅依据上述规范评审,不添加主观意见。
- 严格、精确且有建设性。
- 不解释基础概念,聚焦问题与可执行的修复方案。
- 如果没有提供代码,请要求用户粘贴待评审的代码。
