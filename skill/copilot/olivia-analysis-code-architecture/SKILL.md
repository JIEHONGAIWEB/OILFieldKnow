# Codebase Explorer

一套用于快速拆解陌生代码库、并输出结构化分析报告的方法。核心原则：**先看全局地图，再进入城市细节**——大部分人"看不懂代码"不是代码太复杂，而是一上来就扎进实现细节，跳过了业务语义层和架构层。

## 何时使用

- 用户要求理解/审查一个不熟悉的代码库、模块、或 PR
- Claude 自己准备对一个尚未探索过的代码库做修改之前（先跑一遍本方法，再动手改）
- 审查 AI 生成的代码是否存在过度设计、结构混乱的问题

## 核心方法：三层递进式拆解

不要一开始就读代码实现。严格按顺序推进，每层输出一个"确认点"再进入下一层。

### 第 1 层：业务语义层（这段代码要解决什么问题）

- 看 README、目录名、顶层文件名，先猜一遍这个项目/模块的业务定位
- 找到最能代表"核心业务动作"的一条主流程（比如"用户登录"“下单”"发消息"这种一眼就懂业务含义的操作），不要贪多，先只锁定一条
- 输出：一句话描述"这个系统/模块是做什么的"

### 第 2 层：架构层（数据怎么流转，模块怎么调用）

- 找入口点：路由注册处、main/index 文件、controller 层——从这里开始，而不是从"看起来重要"的文件开始
- 沿着第 1 层锁定的那条主流程，追踪调用链，只记录"谁调用谁"，不看每一层内部怎么实现
- 遇到不熟悉的函数/类，只看它的签名（输入输出），不看函数体
- 找到"状态真正被修改/持久化"的落点（数据库写入、外部 API 调用、缓存写入等）——这是整个系统的重心
- 输出：一张只有 4-6 个节点的调用链草图（文字描述即可，不必画图），标注每个节点的职责（一句话，不展开实现）

### 第 3 层：实现细节层（只在需要时才展开）

- 只针对第 2 层里"看起来有风险"或用户明确要求的模块，才深入到具体实现
- 关注点排序：边界条件处理 → 并发/竞态 → 错误处理 → 安全（注入、权限校验、密钥） → 代码坏味道（重复、过度抽象、职责不清）
- 不要试图理解每一行代码——只标记"这里有问题"或"这里值得注意"的具体位置

## 判断代码是否"过度设计"的检查清单

发现代码"太重"时，用这几条快速判断是真复杂还是过度设计：

- 这个抽象层/接口目前是否只有一个实现？如果是，且没有明确的近期扩展计划，大概率是过度设计
- 配置项/参数是否远超实际使用场景数量？
- 能否用更少的文件/类表达同样的逻辑，而不损失可读性？
- 这层抽象是否是历史遗留的"临时特殊情况处理"堆积而成，而非一次性设计？

## 输出格式：分析报告

完成拆解后，用以下结构输出报告（Markdown，直接在对话中输出，除非用户要求生成文件）：

```markdown
# [项目/模块名] 代码分析报告

## 一句话总结
[这个系统/模块在做什么，业务语义层的结论]

## 架构概览
- 入口点：[文件/路由]
- 主流程：[A → B → C → D，每步一句话职责说明]
- 状态落点：[数据在哪里被真正持久化/修改]

## 关键发现
### 值得注意的设计
- [合理的设计决策，简述原因]

### 潜在风险点
- [具体位置] — [问题类型：边界条件/并发/安全/过度设计] — [简述影响]

## 建议
- [优先级排序的改进建议，如果用户是要做修改而非单纯理解]

## 未深入的部分
- [哪些模块因为超出主流程范围，本次未展开，如需要可进一步分析]
```

## 使用提示

- 报告要克制：第 3 层细节只展开用户关心或确实有风险的部分，不要对整个代码库做逐行讲解
- 如果代码库很大（大型 monorepo），明确告诉用户本次只覆盖了哪条主流程，其余部分需要用户指定后再深入
- 如果是在审查 AI（包括 Claude 自己）生成的代码，优先检查"过度设计检查清单"，这是 AI 生成代码最常见的问题模式
- 输出报告后，如果发现严重风险点（安全漏洞、数据丢失风险），在报告最上方单独提示，不要埋在列表中间
