## 1. 背景:想法

为 WPO 项目创建 Agent,让它:

1. **自主调用**大量 API;
2. **自主分析**数据;
3. **自主调用数据 API**,并**先检查有哪些数据**(数据发现);
4. **直接由 Agent 完成数据创建**,不再通过界面操作;
5. **数据审阅**直接基于 API 返回结果,由 Agent **自行展示**(不依赖预置页面)。

一句话:**从"人操作界面 → 调用 API"变成"人表达意图 → Agent 调用 API → Agent 生成视图"**。

## 2. 目标与范围

### 目标
回答:这个方向有哪些机会、需要什么能力、哪些部分现在就能做、哪些风险必须先解决。

### In Scope
- 数据发现、数据查询、分析、数据创建/修改(模型上传、调度任务等)、结果展示。

### Out of Scope
- 现场设备控制/下发设定值(风险高,明确排除,见 MCP 文档 3.1)。
- 具体 MCP 协议实现细节(见 MCP 文档)。

## 3. 机会分析

### 3.1 五个想法对应的价值

| 想法 | 机会 | 现在的痛点 |
| --- | --- | --- |
| 自主调用多个 API | 一个意图跨多个接口组合完成(如"找出产量异常井→取其 IPR→对比历史") | 用户要在多个页面间手动切换、复制井号、对照数据 |
| 自主分析 | 把工程师的分析套路(工作点、异常排查)变成可复用流程,分析结果可解释 | 分析依赖个人经验,难复制、难沉淀 |
| 数据发现 | Agent 先问"有什么数据、覆盖哪些井/时间",再决定查什么 | 新人不知道系统里有什么数据,入口分散 |
| Agent 创建数据 | 一句话/拖一个文件完成模型上传、任务创建,省去多步表单 | 多步表单、重复填写、操作路径长 |
| Agent 自行展示 | 按问题动态生成表格/图表/摘要,不用为每种问法开发页面 | 每个新视图都要排需求、开发、发布 |

### 3.2 更大的机会(想法之外)

- **批量与长尾操作**:对 50 口井做同一件事,界面要点 50 次,Agent 一次完成。
- **跨模块关联**:WSO、Model Management、Scheduler 之间用户要手动关联,Agent 可以天然串起来。
- **知识内嵌**:把本知识库(领域概念、异常规则、API 清单)作为 Agent 上下文,让输出带口径说明。
- **主动式**:Agent 定期巡检、发现异常主动提示(比被动查询价值更大)。
- **降低培训成本**:新人用自然语言即可上手,不必先学界面。
- **API 反哺**:Agent 使用会暴露接口契约不清、命名不一致等问题,倒逼 API 治理。

## 4. 目标架构(概念)

```
用户(自然语言 / 拖拽文件)
        │
   Agent(规划 + 推理)
   ├─ 数据发现:列出可用数据集、井、时间范围、字段含义
   ├─ 工具层(MCP / Function Calling):只读工具 / 写工具(需确认)
   ├─ 分析层:统计、对比、异常规则、领域公式
   └─ 展示层:表格 / 图表 / 摘要 / 对比卡片(由返回数据生成)
        │
   现有 WPO REST API(鉴权透传、审计)
```

关键点:**Agent 不绕过 API**,所有读写都经现有接口,保持权限与业务规则一致。

## 5. 能力拆解与可行性

| 能力 | 现状/前提 | 可行性 | 备注 |
| --- | --- | --- | --- |
| 只读查询 | WSO Overview 11 条 + Analyze Chart 10 条接口已存在 | 高 | 但部分接口契约"待补充" |
| 数据发现 | **缺少"元数据/目录"类接口**,需新增或在 MCP 层汇总 | 中 | 可先用知识库文档做静态目录,再演进为动态 |
| 分析 | 领域规则在文档中(异常规则手册等),可作为提示/资源 | 中 | 需要评估集验证准确性 |
| 数据创建 | 模型上传、Scheduler 任务有 UI 流程,API 契约需确认 | 中 | 必须有"草稿→确认"机制 |
| Agent 自行展示 | 需要受控的渲染方式 | 中 | 见 5.1 |
| 自主多步调用 | 模型能力足够,关键在工具描述质量 | 高 | |

### 5.1 "自行展示"的三种做法

| 做法 | 描述 | 优点 | 风险 |
| --- | --- | --- | --- |
| A. 文本 + Markdown 表格 | Agent 直接用文字和表格回答 | 最快,零前端开发 | 大数据量、曲线类(IPR)表达差 |
| B. 声明式图表规格 | Agent 输出受限的图表/表格 JSON,前端用现有组件库渲染 | 视觉一致、可控、可复用设计系统 | 需要约定规格与前端渲染器 |
| C. Agent 生成任意前端代码 | 动态生成页面 | 灵活 | 安全、一致性、可维护性差,**不建议**(远期仅限沙箱,见 5.3) |
| D. 动态界面引擎(UI Schema + 动作总线) | Agent 输出界面描述与指令,前端引擎用白名单组件实时组装并响应 | 受控、可审计、可沉淀为看板、可与现有界面并存 | 需建设引擎与组件注册表,**见 5.3** |

**倾向:** 起步 A,中期 B(复用 [design-system](../design-system/README.md) 组件),不做 C。

### 5.2 API 返回后,界面应内置哪些展示工具

**核心原则:Agent 选"画什么",前端决定"怎么画"。** Agent 不输出 ECharts option,只输出一份受限的**可视化规格(VizSpec)**;前端用已有的 `com-chart` / `com-map` 和设计系统渲染。这与 [ADR-0002 数据驱动图表分层](../architecture-decision/0002-data-driven-chart-layering.md)(Business → Data → Metric → Visualization → ECharts)一致:Agent 只工作在 Visualization Model 层,主题、颜色、tooltip 仍由现有 [design-system/charts](../design-system/charts/README.md) 保证。

**建议内置的展示工具(Renderer 白名单):**

| # | 工具 | 适用的数据形态 | WPO 现有对应 | 技术 |
| --- | --- | --- | --- | --- |
| 1 | KPI 卡片 | 单值 + 单位 + 同比/环比/状态 | `esp-production-summaries` | 现有 kpi 组件 |
| 2 | 数据表格 | 多行多列明细;支持排序、筛选、异常高亮、导出 | WSO 明细表(见[异常规则手册](../frontend/ui-patterns/wso-detail-table-exception-rulebook.md)) | 现有表格 + 规则着色 |
| 3 | 趋势折线图 | 时间序列,可多序列、双 Y 轴、阈值线 | `data-analyses`(well-trend) | ECharts line |
| 4 | 对比柱状图 | 分类对比、计划 vs 实际 | `oil-rate-comparison` | ECharts bar |
| 5 | 环形/占比图 | 状态分布、构成占比 | 状态概览 donut | ECharts pie |
| 6 | XY 曲线图(含工作点标记) | 性能曲线交叉 | IPR / Pump / Gas Lift / Inflow | ECharts line/scatter + markPoint |
| 7 | 梯度图(深度剖面) | 深度为 Y 轴(反向),压力/温度为 X | `gradient-plots` | ECharts,Y 轴反向 |
| 8 | Dynacard 闭环图 | 位移-载荷封闭曲线 | SRP dynacard points | ECharts scatter/line |
| 9 | 地图 | 井位 + 状态着色、聚类 | `esp/map` | Leaflet + markercluster |
| 10 | 排名/瀑布图 | Top N、增量潜力 | `oil-gain-potential` | ECharts bar |
| 11 | 仪表/达标图 | 合规率、完成度 | `reservoir-guideline-compliance` | ECharts gauge / progress |
| 12 | 前后对比卡 | 修改前 vs 修改后(写操作确认) | —(新增) | 自定义 diff 组件 |
| 13 | 确认卡(Confirm Card) | 草稿预览 + 确认/取消 | —(新增,写操作必备) | 自定义组件 |
| 14 | 摘要文本 + 引用 | 结论、口径说明、数据来源 | —(新增) | Markdown |
| 15 | 3D(后期) | 井轨迹/油藏 | `webviz-3d` | 暂不纳入 |

> 优先级建议:**1、2、3、4、5、14** 为 MVP;**6、7、8、9、10、11** 随对应 API 契约补全逐步加入;**12、13** 在引入写操作时同步上线;15 不做。

**选图规则(数据形态 → 工具),可写入 Agent 提示与前端校验:**

| 数据形态 | 默认工具 |
| --- | --- |
| 1 个值 | KPI 卡片 |
| 时间 × 数值(1–N 序列) | 趋势折线图 |
| 分类 × 数值 | 对比柱状图(类别 > 15 时改排名图/表格) |
| 占比、状态分布 | 环形图(项 > 8 时合并"其他") |
| 数值 × 数值(性能曲线) | XY 曲线图 |
| 深度 × 数值 | 梯度图 |
| 经纬度 + 属性 | 地图 |
| 明细列表 / 需精确读数 | 数据表格 |
| 无法判断 | 数据表格(安全兜底) |

**VizSpec 示例(Agent 输出,而非 ECharts option):**

```json
{
  "type": "trend",
  "title": "A-12 井近 30 天产油量",
  "source": { "endpoint": "wpo/wells/{wellId}/optimizations/data-analyses", "params": {"wellId": "A-12", "range": "30d"}, "fetchedAt": "2026-11-10T09:30:00Z" },
  "x": { "field": "date", "type": "time" },
  "series": [{ "field": "oilRate", "name": "Oil Rate", "unit": "bbl/d", "yAxis": 0 }],
  "thresholds": [{ "value": 800, "label": "目标值" }],
  "notes": ["产量为分摊后数据,口径见异常规则手册"]
}
```

**每个展示结果必须附带(通用能力,不是单独工具):**

- **数据来源与时间**:调用了哪个接口、哪些参数、何时取的数,点击可展开原始数据——这是建立对 Agent 分析信任的关键。
- **单位与口径说明**:沿用接口返回的单位;分摊算法、异常规则等口径以脚注形式附上。
- **空态/错误态/部分数据**:无数据、接口超时、仅部分井有数据时,明确告知,而不是画一张空图。
- **大数据处理**:点数过多时降采样并提示;表格分页/虚拟滚动;一次最多返回 N 行,超出让用户确认继续。
- **交互基础能力**:缩放、图例开关、tooltip、导出(PNG/CSV)、复制数据。
- **深链回到原界面**:"在 WSO 中打开此井",保证复杂分析仍可回到完整界面。
- **主题与一致性**:自动跟随明暗主题,复用 `com-chart` 的 tokens。
- **多视图组合**:一次回答可组合为"摘要 + KPI + 图 + 表"的看板卡片,而不是单图。

**安全约束:**

- 只接受白名单 `type`,字段名必须来自 API 返回,**不执行 Agent 输出的 HTML/JS**。
- VizSpec 用 JSON Schema 校验,不合法时降级为表格 + 文本。
- 数据在前端从原始 API 结果映射,**Agent 只给映射关系,不转抄数值**,避免模型"抄错数"导致图表与事实不一致。

**关键设计点:** 最后一条尤其重要——让 Agent 引用数据而不是复述数据(`dataRef` + 字段映射),图上每个数字都能追溯到接口返回。

### 5.3 想法:Agent 结果直接驱动前端 —— 动态界面运行引擎(Agent UI Runtime)

5.2 解决的是"一张图怎么画"。这里把想法再往前推一步:**Agent 的返回结果不只是被展示,而是直接操作一个前端项目**——前端内置一个"动态运行界面的引擎",Agent 输出的是**界面描述与界面指令**,引擎负责把它们实时变成可交互的界面。

> 一句话:**前端不再只是预先写好的页面集合,而是一个可被 Agent 编排的界面运行时(UI Runtime)**。

#### 5.3.1 三个层次的"操作前端"

| 层次 | Agent 能做什么 | 示例 | 难度/风险 |
| --- | --- | --- | --- |
| L1 指令式:操作现有界面 | 发出受控指令:导航、切换 Tab、设置筛选条件、选中井、缩放地图、打开面板 | "把地图聚焦到 A 区块,筛出 ESP 井并打开 Oil Rate 对比" → `navigate` + `setFilter` + `openPanel` | 低;复用现有页面与状态,最先落地 |
| L2 声明式:动态组装界面 | 输出界面描述(Schema),引擎用白名单组件拼出新页面/看板 | "给我一个异常井排查看板:左边地图,右上 KPI,右下异常明细表" | 中;需要组件注册表与布局系统 |
| L3 生成式:动态生成代码 | Agent 生成组件代码,在沙箱中编译运行 | "写一个自定义的产量分摊对比视图" | 高;安全、一致性、可维护性风险最大 |

**倾向:L1 + L2 为主线;L3 仅作为远期/开发者模式,且必须在沙箱里运行。**

#### 5.3.2 引擎的组成

```
Agent 输出(UI Schema / UI Action)
        │
┌───────▼────────────────────────────────────────────┐
│  Agent UI Runtime(前端内置引擎)                    │
│  1. 协议层     解析 + JSON Schema 校验 + 版本管理    │
│  2. 组件注册表 白名单:KPI/表格/图表/地图/确认卡…     │
│  3. 布局引擎   网格/分栏/标签页/卡片流               │
│  4. 数据绑定   dataRef → API 结果;刷新/轮询/联动    │
│  5. 动作总线   navigate/setFilter/openPanel/...      │
│  6. 状态管理   视图状态可保存、回放、撤销            │
│  7. 事件回传   用户点击/选择 → 回传给 Agent          │
│  8. 安全与降级 校验失败 → 表格+文本;权限与审计      │
└───────┬────────────────────────────────────────────┘
        │ 渲染
   现有 Angular 组件库(com-chart / com-map / 表格 / 设计系统)
```

要点:

- **组件注册表(Component Registry)**:把现有组件登记为"Agent 可用组件",每个组件声明名称、props 的 JSON Schema、可触发的事件。Agent 能用什么由注册表决定;新增能力 = 注册新组件,不改引擎。Angular 下可用动态组件加载(如 `ngComponentOutlet` / `ViewContainerRef.createComponent`)按 `type` 实例化。
- **动作总线(Action Bus)**:L1 指令的统一入口,每个动作有名称、参数 Schema、权限等级(只读 / 需确认)。例如 `navigate`、`setFilter`、`selectWell`、`openPanel`、`focusMap`、`exportData`。**写类动作(创建模型、创建任务)只能通过确认卡触发**。
- **数据绑定**:界面描述里只写 `dataRef`(接口 + 参数)和字段映射,引擎自己取数并渲染,沿用 5.2 的"Agent 不复述数值"原则;组件之间可声明联动(点地图上的井 → 表格和曲线图同步刷新)。
- **双向通道**:用户在动态界面里的点击、框选、筛选,作为事件回传给 Agent(例如"用户选中了这 3 口井"),Agent 据此继续下一步——这使对话与界面成为一个闭环,而不是"问一次画一次"。
- **状态可保存**:动态生成的界面可以"固定为看板"、命名、分享、回放;这相当于把 Agent 的一次分析沉淀为可复用的页面。
- **版本与兼容**:UI Schema 带版本号;组件升级时保持向后兼容,避免旧看板失效。

#### 5.3.3 UI Schema 与 UI Action 示例

动态组装一个看板(L2):

```json
{
  "schemaVersion": "1.0",
  "layout": { "type": "grid", "columns": 12 },
  "items": [
    { "id": "map",  "component": "map",   "span": [0, 0, 6, 8],
      "data": { "ref": "wpo/wells/esp/map", "params": { "area": "A" } },
      "emits": ["wellSelected"] },
    { "id": "kpi",  "component": "kpi",   "span": [6, 0, 6, 2],
      "data": { "ref": "wpo/wells/esp-production-summaries" } },
    { "id": "tbl",  "component": "table", "span": [6, 2, 6, 6],
      "data": { "ref": "wpo/wells/status/overview" },
      "listensTo": [{ "from": "map", "event": "wellSelected", "bindTo": "filter.wellId" }] }

```

```json
[
  { "action": "navigate",  "args": { "route": "wso/overview" } },
  { "action": "setFilter", "args": { "area": "A", "method": "ESP" } },
  { "action": "openPanel", "args": { "panel": "oilRateComparison" } }

```

#### 5.3.4 与现有前端的衔接

- 现有技术栈(Angular + ECharts 6 + Leaflet,见 [frontend/charts](../frontend/charts/README.md))可直接作为渲染层,不需要重写。
- 现有 WSO 图表面板已是"容器 + 展示组件 + 数据驱动"的结构(见 [wso-chart-panel-architecture.md](../frontend/charts/wso-chart-panel-architecture.md)、[adding-a-business-layer.md](../frontend/charts/adding-a-business-layer.md)),可作为**组件注册表的第一批候选**,工作量主要在"把组件的输入输出标准化为 Schema"。
- 状态层面,Agent 的动作应复用现有的路由与状态(见 [frontend/state](../frontend/state/README.md)、[frontend/routing](../frontend/routing/README.md)),而不是另建一套,保证"Agent 操作的结果"和"用户手动操作的结果"完全一致。

#### 5.3.5 与"完全生成代码"的对比

| 维度 | L2 声明式 Schema 引擎 | L3 Agent 生成代码 |
| --- | --- | --- |
| 安全 | 只能用白名单组件,可校验 | 需沙箱,难以完全约束 |
| 一致性 | 复用设计系统,风格统一 | 容易偏离设计规范 |
| 可审计 | Schema 可存储、diff、回放 | 代码审查成本高 |
| 灵活性 | 受限于注册表 | 几乎无限 |
| 维护 | 组件升级集中处理 | 生成物各自为政 |
| 结论 | **主线方案** | 仅限开发者模式/原型验证 |

#### 5.3.6 该引擎带来的新机会与新风险

机会:
- **界面按需生成**:不再为每个新问法开发页面,长尾分析需求直接满足。
- **分析可沉淀**:一次对话的产出可固定为看板,推广为团队资产。
- **与界面并存**:L1 指令让 Agent 成为现有界面的"遥控器",老用户习惯不被打破。
- **组件复用率提升**:组件注册表倒逼组件标准化,也利于后续的 Agent 与非 Agent 场景共用。

风险与对策:
- **界面不可预期**:同一问题两次生成布局不同 → 提供布局模板与"固定看板"能力,限制自由度。
- **越权动作**:Agent 通过动作总线触发不该触发的操作 → 动作分级、写类强制确认、按用户权限校验。
- **性能**:一个看板同时触发多个接口 → 引擎统一限流、缓存、并发控制。
- **状态污染**:Agent 修改筛选后用户困惑 → 所有 Agent 动作可见、可撤销、有"由 Agent 修改"的标识。
- **调试困难**:界面由模型生成,出问题难复现 → 记录每次的 Schema 与动作日志,支持回放。

### 5.4 小结:展示能力的演进梯度

```
文本/表格 ──► 声明式图表(VizSpec) ──► 动态界面引擎(UI Schema + Action Bus) ──► (远期)沙箱生成代码
   阶段1            阶段3                        阶段3.5 / 4                           仅开发者模式
```

### 5.5 流程沉淀方式的转变:从"请别人定义"到"自己沉淀并验证可复用"

> 注:下文把"金石"理解为"经过检验、可作为标准的流程基石(沉淀物)"。若指某个具体的流程平台/工具,请告知,我再对齐表述。

#### 5.5.1 转变

| 维度 | 以前:请别人来定义流程 | 现在:用户借助 Agent 自己沉淀流程 |
| --- | --- | --- |
| 谁来定义 | 顾问/专家/开发先访谈、再设计、再实现 | 一线用户在真实工作中边做边沉淀 |
| 来源 | 访谈与假设,容易与实际脱节 | 真实操作轨迹(做过什么、调了哪些接口、在哪里判断) |
| 周期 | 立项、排期、开发、发布,周/月级 | 一次对话即可产出初稿,分钟/小时级 |
| 成本 | 高,每个流程都要投入开发 | 低,边际成本接近零 |
| 变更 | 改流程要重新走开发 | 用户直接调整并重新验证 |
| 风险 | 做出来没人用 | **沉淀出来的流程可能只对一个场景有效** → 必须测试可复用性 |

关键变化:**流程的"作者"变成使用者,专家的角色从"定义者"变成"评审者/验证者"**;而"这个流程是否真的可复用",成了新的核心问题,需要有一套测试方法,而不是靠人感觉。

#### 5.5.2 沉淀闭环

```
① 做一次(用户 + Agent 完成真实任务,如"某井异常排查")
      │  记录轨迹:意图、调用的接口与参数、分析步骤、展示的视图、人工确认点
② 提炼(Agent 把轨迹抽象为流程:步骤 + 参数化 + 前置条件 + 输出)
      │
③ 测试可复用性(换井/换时间/换区块回放,比对结果)   ← 本节重点
      │
④ 评审与发布(专家审、版本化、进入流程库)
      │
⑤ 使用与反馈(使用率、成功率、失败原因回流)
      │
⑥ 迭代或下线
```

#### 5.5.3 流程资产应包含什么

沿用本仓库已有的 Skill/Agent 思路(见 [skill/](../skill/README.md)、[agents/](../agents/README.md)),一个流程资产建议包含:

- **名称与目的**:解决什么问题,适用于什么场景,不适用于什么。
- **输入参数**:井号、时间范围、区块、生产方式等,而不是写死某口井。
- **步骤序列**:每步调用的工具/接口、判断条件、分支。
- **数据契约**:依赖哪些 API 与字段(契约变动时可自动发现失效)。
- **输出**:UI Schema / VizSpec(见 5.2、5.3)与结论模板,含口径说明。
- **人工检查点**:哪些步骤必须人确认(尤其是写操作)。
- **版本、作者、评审人、权限范围**。
- **验证记录**:历史测试结果(通过率、覆盖的场景)。

#### 5.5.4 如何测试流程的可复用性

| 测试类型 | 做法 | 回答的问题 |
| --- | --- | --- |
| 参数泛化测试 | 同一流程换 N 口不同井/不同时间段/不同生产方式运行 | 是否只对原来那口井有效?(防过拟合) |
| 重放回归测试 | 用保存的参数 + 保存的接口响应(录制回放)重复运行,比较输出 | 流程本身是否稳定?模型改动后结果是否漂移? |
| 黄金样例比对 | 为若干代表性场景由专家给出"正确结论",流程输出与之比对 | 结论是否正确(不仅是能跑通)? |
| 边界/异常测试 | 无数据、部分字段缺失、接口超时、极端值、新井(数据不足) | 遇到异常是否优雅降级并提示,而不是编造? |
| 契约漂移测试 | API 字段或口径变化后重跑 | 能否及时发现流程已失效? |
| 多人复现测试 | 不同用户、不同权限范围执行 | 是否依赖作者个人环境/权限? |
| 稳定性测试 | 同一输入多次运行(模型有随机性) | 步骤与结论是否一致? |
| 人工评审 | 专家审阅步骤与口径 | 业务逻辑是否合理、口径是否被误用? |

**可复用性指标(建议):**

- **泛化通过率** = 通过的测试场景数 / 总测试场景数(例如 ≥ 80% 才允许发布)。
- **结论一致率**:与黄金样例一致的比例。
- **降级正确率**:异常场景下正确提示而不是编造的比例。
- **稳定性**:重复运行结果一致的比例。
- **使用后指标**:被不同用户复用次数、成功完成率、人工修改比例(修改越多说明越不可复用)。

**发布分级(建议):**

| 等级 | 条件 | 可见范围 |
| --- | --- | --- |
| 草稿 | 仅作者验证过一次 | 仅自己 |
| 试用 | 通过泛化与重放测试 | 小组 |
| 推荐 | 通过黄金样例并经专家评审 | 全员 |
| 标准 | 长期使用指标良好 | 纳入标准流程库,作为"金石" |

#### 5.5.5 风险与对策

- **错误流程被放大**:一个有口径错误的流程被多人使用 → 分级发布、专家评审、结果附口径说明。
- **过拟合单一案例**:参数写死、只适用于某口井 → 强制参数化 + 泛化测试。
- **所有权不清**:流程无人维护 → 记录作者/评审人,契约漂移时通知。
- **流程泛滥**:大量低质量流程 → 使用率和成功率驱动下线。
- **权限**:流程中的写操作仍按执行者权限校验,不因"流程已发布"而放宽。

#### 5.5.6 与本方案其他部分的关系

- 5.2 / 5.3 提供**输出形态**(VizSpec / UI Schema),流程资产直接引用;
- 第 7 节的**评估集**可与这里的黄金样例合并建设;
- 第 9 节路线新增"流程沉淀与可复用性验证"阶段。

## 6. 方案对比:Agent 的角色

| 方案 | 描述 | 优点 | 风险/缺点 | 结论 |
| --- | --- | --- | --- | --- |
| 1. Agent 作为辅助入口(与界面并存) | 保留界面,Agent 作为第二入口 | 风险低,可渐进,用户可回退 | 两套入口需保持一致 | **推荐起步** |
| 2. Agent 取代界面做数据创建 | 创建类操作只走 Agent | 体验统一 | 无兜底,出错无人工路径;审计/权限压力大 | 需前置条件满足后再评估 |
| 3. 完全 Agent 化(含展示) | 界面基本被替代 | 终极形态 | 可靠性、可解释性、合规要求最高 | 长期愿景,非近期目标 |

## 7. 关键风险(必须先回答)

1. **正确性**:工程场景下 Agent 的分析若出错,后果比普通应用大。需要**评估集**(问题→期望调用→期望结果)与口径说明,结果须可追溯到原始 API 数据。
2. **写操作安全**:"不再通过界面创建数据"意味着写操作全落在 Agent 上。必须有:草稿→确认→执行、可撤销/可回滚、审计日志、覆盖既有数据的二次确认。
3. **权限**:以当前用户身份调用,按井/资产范围过滤;Agent 不得拥有超出用户的权限。
4. **提示注入**:上传文件内容、井名称等可能诱导 Agent 执行写操作;工具层要有独立于模型的校验。
5. **API 契约不全**:大量接口用途/字段"待补充",Agent 会误用。**这是首要阻塞**。
6. **数据口径复杂**:分摊算法、异常规则需随结果一起返回,避免误导。
7. **可观测与成本**:模型调用成本、延迟、批量调用对后端的压力,需限流与监控。
8. **合规**:内网/云环境对外部模型调用的限制,可能决定模型部署方式。
9. **UI 不能完全消失**:审阅关键数据、复杂图表、需要精细交互的场景,界面仍有优势;Agent 取代的应是"重复/多步操作",而不是所有交互。

## 8. 影响评估

- 业务影响:提升分析与操作效率;改变工程师工作方式,需要培训与信任建立。
- 数据模型影响:基本无;可能需新增元数据/目录与审计表。
- API 影响:**最大**——需补全契约、统一路由前缀、可能新增数据发现与"草稿/确认"类接口。
- 前端影响:短期小(Markdown 展示);中期需图表规格渲染器。
- 测试影响:新增 Agent 评估集与回归;写操作需端到端测试。
- 发布/回滚影响:Agent 与界面并存时回滚简单;取代界面后需更严格的灰度。

## 9. 建议路线

| 阶段 | 内容 | 退出标准 |
| --- | --- | --- |
| 0 准备 | 补全 WSO API 契约;列出"数据目录"(有哪些数据、含义、口径) | 目标接口 100% 有用途与字段说明 |
| 1 只读 PoC | 数据发现 + 查询 + 简单分析 + Markdown/表格展示 | 评估集准确率达标;鉴权透传验证 |
| 2 写操作(受控) | 模型上传、Scheduler 任务:草稿→确认→执行,带审计 | 未确认不创建;可回滚 |
| 3 受控展示 | 声明式图表规格(VizSpec)+ 前端渲染器,按 5.2 的工具清单与优先级逐个加入 | 与现有设计系统一致;规格校验失败可降级为表格 |
| 3.5 界面运行引擎 | L1 动作总线(navigate/setFilter/openPanel)→ L2 组件注册表 + UI Schema + 事件回传,固定为看板 | Agent 与手动操作结果一致;Schema 校验失败可降级;动作可撤销可回放 |
| 3.8 流程沉淀与复用验证 | 记录操作轨迹 → 提炼参数化流程 → 泛化/重放/黄金样例测试 → 分级发布(见 5.5) | 至少 1–2 个流程通过泛化测试并被他人复用 |
| 4 主动巡检 | 定时巡检、异常提醒 | 误报率可接受 |
| 5 评估取代界面 | 基于使用数据判断哪些创建流程可以只走 Agent | 兜底与审计齐备 |
