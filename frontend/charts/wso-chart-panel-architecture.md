# WSO Chart Panel Architecture (current implementation)

Analysis of the chart components actually shipped in `libs/wso`. This documents the
*as-built* pattern and its extensibility, and complements
[ADR-0002 (data-driven chart layering)](../../architecture-decision/0002-data-driven-chart-layering.md),
which describes the *target* layered pipeline.

- Status: Descriptive (as-built as of 2026-07-24)
- Scope: `libs/wso/src/lib/components/chart/**`

## Source map (`wpo-app`)

| Concern | Source path |
| --- | --- |
| Chart card (dumb) | `libs/wso/src/lib/components/chart/wso-chart-panel/wso-chart-panel.component.ts` |
| View/page switcher (dumb) | `libs/wso/src/lib/components/chart/chart-view-switcher/chart-view-switcher.component.ts` |
| Container (smart) | `libs/wso/src/lib/components/wso-overview/wso-overview.component.ts` |
| Chart data models | `libs/wso/src/lib/shared/models/wso-chart.model.ts` |
| Data source | `libs/wso/src/lib/services/wso-mock-data.service.ts` (`getChartPages`) + `shared/services/wso-api.service.ts` |
| Shared renderer | `libs/shared/src/lib/components/com-chart/` (`CommonChartOptionsLite`) |

## Pattern

**Container / Presentational + declarative data-driven rendering.** Three layers:

```
WsoOverviewComponent  (Smart: signals, data fetch, state orchestration)
        │  [chart] / [views] data
        ▼
WsoChartPanelComponent · ChartViewSwitcherComponent  (Dumb: @Input / @Output only)
        │  [options]
        ▼
com-chart (shared)  →  ECharts     (renders whatever the options object describes)
```

| Layer | Responsibility |
| --- | --- |
| Data source | Produces `WsoChartPageModel[]`; every chart is described as an `options` object |
| Container (Smart) | Holds `chartPages`, `activeChartViewId`, `activeChartId` signals; fetch, theme sync, view switching |
| Presentational (Dumb) | Pure `@Input`/`@Output`; no state, no business logic |
| Renderer | `com-chart` renders uniformly from `CommonChartOptionsLite`; chart is fully data-defined |

## Is it data-driven? — Yes

Evidence in code:

1. Charts are described as data, not hard-coded templates: `WsoChartModel { id, options, configurable?, sliderValue? }` and the render contract `CommonChartOptionsLite { title, chartOptions, columns, data, actions }`.
2. Views are generated by iterating data: `*ngFor="let chart of page.charts"`.
3. Switching/highlighting are id-driven: `activeChartViewId()`, `activeChartId()`, `views.findIndex(v => v.id === activeViewId)`.
4. Presentational components are stateless: `WsoChartPanelComponent` only emits `activate`/`detail`; `ChartViewSwitcherComponent` projects content via `@ContentChild('viewItem')`.

The set of "how many tabs, how many charts per tab, what each chart looks like" is
entirely decided by the data returned from `getChartPages()` (or API mapping).

## Extensibility for new business layers

### Supported out of the box
- **Add a tab / chart**: push a new `WsoChartPageModel` / `WsoChartModel` into `getChartPages()` (or the API mapper). Container and presentational layers do not change.
- **Swap data source**: `USE_WSO_API` flag + `mapSummaryToCards` already demonstrate mock → API switching; a new business layer only supplies a new mapper.

### Coupling points — refactored to data-driven (2026-07-24)
The three coupling points below were refactored so a new business layer can be added
by editing data only, not the container or dumb components.

1. **Well-scope strategy is now data on the page model** — `WsoChartPageModel.wellScope: 'all' | 'even' | 'odd'` replaces the hard-coded `viewId === 'allocation' | 'potential'` branches. `WsoOverviewComponent.chartScopedWellMeta` reads `activeChartPage()?.wellScope` and delegates to `applyWellScope()`. (The previously dead `'allocation'` branch — page ids are `'production'`/`'potential'` — is gone; effective behavior preserved: `potential → 'odd'`, others `'all'`.)
2. **Toolbar is declarative** — `WsoChartModel.toolbarControls: WsoChartToolbarControl[]` replaces the `configurable: boolean` + hard-coded `"Last Test Rate"` slider. `wso-chart-panel.html` renders controls generically via `*ngFor` (currently `kind: 'slider'`; extend the union for new control kinds). Values tracked per control id in `sliderValues`.
3. **Type-keyed chart builder registry** — `WsoMockDataService` now resolves options through `chartOptionBuilders` (a mapped-type `Record<type, builder>`) + `buildChartOptions(spec)`. Pages are declared as data (`getChartPageSpecs()` → `WsoChartPageSpec[]` with a `WsoChartOptionSpec` union). Adding a chart type = add one union member + one registry entry (OCP, no if/else) — matches ADR-0002's Builder/Registry layer.

### Remaining consideration
- **Variable chart count — verified adaptive.** `wso-overview.html` renders `*ngFor="let chart of page.charts"` with no hardcoded count, and the layout is a flex column (`wso-overview__chart-group { display: flex; flex-direction: column }`) where each host uses `flex: 1 1 0`. So a page with 1 / 2 / 3+ charts divides the available height evenly (1 → full, 2 → half, 3 → third) without code changes. The model comment "side by side" was corrected to "groups charts under one tab".

## Conclusion

- **Pattern**: container/presentational + declarative data-driven — sound and mainstream.
- **Data-driven**: yes.
- **Extensibility**: the core path (data → iterate → render) is extensible; the three
  former coupling points (`viewId` scope, toolbar, builders) are now data/strategy in
  the model + a type-keyed registry, so a new business layer can be added by editing
  data (`getChartPageSpecs()` / model fields) without touching the container or dumb
  components.
